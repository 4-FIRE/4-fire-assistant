# 架构原则

目标：让维护者可以局部理解和安全修改系统，不必先掌握全部实现。当前模块见[技术设计](technical-design.md)，外部调用规则见[能力与权限设计](capability-design.md)。

## 1. 明确责任

按业务含义和变化原因划分模块。每条规则、每份状态只有一个责任归属。共同变化的内容放在一起，独立变化的内容保持分离。

工具拥有完整契约与执行适配。服务拥有业务决定和状态转换。存储负责可靠保存，接入负责协议，UI 负责展示与用户选择。

## 2. 使用宿主能力

优先使用 Pi 的工具、UI、资源发现、配置和会话。ffa 补充工作区业务能力，不另建主 Agent、插件平台或通用任务运行时。

角色在文档中定义，专业方法在技能中说明。普通研究方法变化不应要求修改底层代码。提示词不能代替程序权限检查。

## 3. 限制依赖

依赖必须显式且单向，避免循环和共享可变状态。模块只取得必要数据与窄能力，不传递完整宿主上下文。

业务规则不随界面或协议变化而重写。命令与工具使用同一服务，不能因入口不同绕过规则。自动检查保护稳定的依赖边界。

## 4. 控制状态与副作用

明确资源的创建、修改、失效和释放责任。工具绑定工作区实例，关闭后旧引用失效。

批准在实际发送入口检查。发送尝试先可靠保存，再调用外部能力。结果未知不等于没有执行；取消和聊天恢复不回滚外部副作用。

能力事实、用户权限和验证证据分别保存。角色约定不构成隔离，协议成功不证明业务完成。

## 5. 保持简单

只为已确认的需求建立抽象。删除无用代码，不增加转发层、默认字段适配或旧格式转换。

不建立固定研究流程、后台自动交易或第二套任务恢复机制。不增加文件哈希校验。不迁移、重建或删除用户工作区与历史交易记录。

若局部需求反复牵动无关模块，先检查责任划分，不继续堆叠补丁。

## 6. 验证真实风险

测试业务规则、契约和关键失败路径，不测试文档措辞、标签或实现结构。使用真实本地文件、SQLite、进程、计算和 Pi SDK，不使用假模型或模拟能力提供方。

真实模型与外部服务需获准环境验收。本地通过不证明外部行为正确，也不代表可以投入实盘。保留未验证边界，不以降低约束替代验证。

## 7. 只维护当前说明

README 提供安装、使用入口和关键风险。`docs/` 保留当前目标、架构、设计理由与注意事项。字段和操作细节放在对应参考资料，避免重复维护。

行为变化时更新所属说明，不追加实施步骤、排查流水或完成清单。必要的设计理由并入当前规则，不保留已完成方案作为另一套事实来源。

使用短句和一致术语。每段说明一个主题，明确条件、动作、结果和限制。精简不能删除重要例外或不确定性。
