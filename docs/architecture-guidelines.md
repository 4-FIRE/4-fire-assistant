# 架构原则

目标：让维护者可以局部理解和安全修改系统，不必先掌握全部实现。当前模块见[技术设计](technical-design.md)，外部调用规则见[能力与权限设计](capability-design.md)。

## 1. 明确责任

按业务含义和变化原因划分模块。每条规则、每份状态只有一个责任归属。共同变化的内容放在一起，独立变化的内容保持分离。

工具拥有完整契约与执行适配。服务拥有业务决定和状态转换。存储负责可靠保存，接入负责协议，UI 负责展示与用户选择。

保留顶层分层，在层内按领域聚合共同维护的文件。工具 schema 与所属工具放在同一领域目录；只有多个领域确实共用的逻辑才放在共享位置。不为目录对称创建空模块，也不增加只做转发的入口文件。

## 2. 使用宿主能力

优先使用 Pi 的工具、UI、资源发现、配置和会话。ffa 补充工作区业务能力，不另建主 Agent、插件平台或通用任务运行时。

角色在文档中定义，专业方法在技能中说明。普通研究方法变化不应要求修改底层代码。提示词不能代替程序权限检查。

## 3. 限制依赖

依赖必须显式且单向，避免循环和共享可变状态。模块只取得必要数据与窄能力，不传递完整宿主上下文。

业务规则不随界面或协议变化而重写。命令与工具使用同一服务，不能因入口不同绕过规则。自动检查保护稳定的依赖边界。

## 4. 控制状态与副作用

明确资源的创建、修改、失效和释放责任。工具绑定工作区实例，关闭后旧引用失效。

批准在实际发送入口检查。发送尝试先可靠保存，再调用外部能力。结果未知不等于没有执行；取消和聊天恢复不回滚外部副作用。

能力事实、用户权限和验证证据分别保存。角色约定不构成隔离，协议成功不证明业务完成。

## 5. 保持简单

只为已确认的需求建立抽象。删除无用代码，不增加无用转发层。插件只支持当前工作区格式，不包含升级命令或历史兼容代码。后续升级由用户手动执行 `scripts/` 中的独立脚本；正常加载不迁移或静默补字段。

对已有的独立变化点使用窄策略，例如 CLI 与 MCP 的调用预览、原生绑定和发送。共同的批准、状态转换与持久化规则留在所属服务，不随协议实现复制。策略使用显式装配清单；新增协议需要扩展契约、校验与装配，但不应改写稳定业务流程。只有一种实现或严格状态分支时，保留直接代码。

不建立固定研究流程、后台自动交易或第二套任务恢复机制。不增加文件哈希校验。实际升级脚本须先要求停止工作区，声明支持的源与目标，变更前备份，变更后验证，支持中断后显式接续。不通过重建或删除数据修复用户工作区，不删除历史交易记录，不重放外部调用。

若局部需求反复牵动无关模块，先检查责任划分，不继续堆叠补丁。

## 6. 验证真实风险

测试业务规则、契约和关键失败路径，不测试文档措辞、标签或实现结构。使用真实本地文件、进程、计算和 Pi SDK，不使用假模型或模拟能力提供方。

真实模型与外部服务需获准环境验收。本地通过不证明外部行为正确，也不代表可以投入实盘。保留未验证边界，不以降低约束替代验证。

## 7. 只维护当前说明

README 提供安装、使用入口和关键风险。技术设计负责模块、生命周期和验证总览；能力与权限、专家协作、文件存储各自维护专题契约。字段和操作方法放在对应参考资料，总览使用链接，不重复展开。

同一主题只保留当前有效说明，旧版本查 Git 历史，不另存文档副本。使用方法、业务行为、接口或架构边界变化时更新所属说明；无需因每次内部实现或 UI 外观调整改写总览。必要的设计理由并入当前规则，不追加实施步骤、排查流水或完成清单。

运行时提示词与说明文档分开维护，不把无需模型感知的实现细节加入提示词。

使用短句和一致术语。每段说明一个主题，明确条件、动作、结果和限制。精简不能删除重要例外或不确定性。
