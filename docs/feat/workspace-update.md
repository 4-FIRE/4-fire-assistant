# `/ffa update` 工作区升级设计

状态：命令、逐版升级服务、备份和专用工具已实现；真实模型流程尚待获准环境验收。

当前目标工作区版本为 1，没有高于 1 的升级要求或生产脚本。有效的现有工作区执行 `/ffa update` 时报告无需升级。本文说明当前升级框架及后续每版脚本必须满足的契约。领域术语见 [CONTEXT.md](../../CONTEXT.md)，现有实现见[技术设计](../technical-design.md)。

## 1. 目标与边界

插件更新方式取决于安装来源：本地路径包由用户更新来源目录的源码和依赖；其他来源按所用 Pi 版本的包管理命令更新。`/ffa update` 将现有工作区适配到已安装插件支持的目标工作区版本，不下载或安装插件。

升级覆盖与 ffa 有关的工作区资料和内部状态，包括 `.ffa/` 内的文件。程序与模型共同完成升级：程序处理内部状态，模型处理资料内容。

内置技能、角色和提示词随插件直接替换。它们不复制到工作区，不由模型合并或修改。已有工作区文档不能用新模板整份覆盖。

升级必须保留投资目标、用户约束、研究结论和历史证据。不发送交易，不重放外部调用，不改写历史执行事实。结果不明记录仍按原有规则核对。

本次设计处理资料和当前存储格式内的状态更新。未来存储格式变化由对应工作区版本的定制脚本处理，不建立通用格式转换或兼容机制。

当前仓库仍拒绝不支持的格式，并禁止迁移。未来实现定制格式升级时，须同步修改相关规则和加载入口，不能用本设计推定现有代码已经支持迁移。

## 2. 三类版本

| 版本 | 含义 | 更新规则 |
| --- | --- | --- |
| 插件版本 | ffa 软件包版本 | 用户按安装来源更新源码或使用 Pi 包管理命令 |
| 工作区版本 | 资料和内部状态应符合的要求 | 使用独立整数，逐版本升级 |
| 存储格式版本 | 状态文件和数据库的结构契约 | 仅在实际格式变化时单独处理 |

工作区版本从 1 开始。引入工作区版本不改变当前 `ffa-pi/1` 和业务数据库版本 1。插件更新但工作区要求未变时，不增加工作区版本。

没有工作区版本记录的现有工作区，通过有效的 `ffa-pi/1` 状态识别为基础版本 1。找不到该标识时不处理，不自动初始化，不收养未知目录。已有显式版本不能被基础版本识别覆盖。

程序在现有 SQLite 账本中保存独立的工作区版本、批次、已确认方案和阶段。完成版本与该版历史在同一事务中保存。二者含义不同：阶段完成不代表整个版本已升级。

## 3. 命令行为

仅初始化完成的工作区可以执行 `/ffa update`。未初始化或初始化未完成时，引导用户使用 `/ffa init`，不执行升级。

启动时可以提示有可用升级，但不自动执行。用户显式执行命令后，程序检查工作区版本和已安装插件提供的升级链。

| 条件 | 行为 |
| --- | --- |
| 已达到目标版本且没有未完成阶段 | 报告无需升级；不写入、不备份、不启动模型任务 |
| 存在完整升级链 | 开始方案准备，或接续未完成阶段 |
| 缺少升级脚本或说明 | 停止，报告缺失节点 |
| 工作区版本高于插件支持版本 | 停止，不降级 |
| 工作区状态无法识别或读取 | 不处理，不覆盖已有状态 |

升级期间建议暂停日常业务，但不增加强制业务锁。这是操作建议，不是并发隔离保证。程序仍须使用现有工作区写入所有权及可靠存储规则。

## 4. 每版升级契约

每次工作区版本更新均提供独立脚本和独立说明。源版本为 `N`，目标版本为 `N+1`，不跳过中间版本。

### 4.1 程序脚本

脚本及其配套声明负责：

- 明确源版本、目标版本和适用条件。
- 执行不修改状态的预检查。
- 声明内部变更摘要及备份范围。
- 执行该版内部状态变更。
- 提供程序阶段的验证条件。
- 保证重复执行安全，并识别已完成的效果。

没有内部变更的版本也提供明确的空操作脚本。不允许模型生成临时脚本来代替包内的版本脚本。

脚本只处理该版本明确要求的变化。权限变更必须出现在用户确认的摘要中，不能通过补全字段静默放宽权限。

### 4.2 模型升级说明

说明明确：

- 该版资料要求的变化及适用条件。
- 必须修改的资料和条件适用的资料。
- 禁止修改的内容。
- 可检查的完成条件及必须保留的事实。

说明不向模型暴露 `.ffa/` 结构、内部文件路径或备份内容。程序向模型提供业务层面的变更摘要和阶段结果。

模型可以读取相关资料以判断适用性，但不能借升级重新整理整个工作区。缺少事实时报告缺项，不编造历史证据。

## 5. 执行流程

从版本 1 升到版本 3，必须先完整完成 `1→2`，再执行 `2→3`。每版均有独立备份和完成节点。某版失败时，不执行后续版本。

可以按版确认，也可以用 `following` 提交后续版本方案，一次确认整个升级方案。执行中新增修改范围或改变已确认方案时，必须补充确认。程序保存声明和说明原文；接续时发现变化，先返回方案准备阶段，不执行新变更。

每版流程如下：

1. 程序检查版本、升级链和脚本适用条件，不修改状态。
2. 程序提供升级说明及内部变更摘要。
3. 模型读取相关资料，整理文档修改方案和具体文件清单。
4. 用户确认程序变更摘要及文档修改方案。
5. 程序在 `.ffa/` 内保存升级前备份。
6. 程序执行该版脚本并验证内部变更。
7. 程序阶段成功后，模型按方案合并工作区文档。
8. 模型提交已修改、无需修改和未解决项。
9. 专用完成工具检查程序阶段和该版可检查的资料条件。
10. 用户确认该版完成后，程序可靠记录目标工作区版本。
11. 有后续版本时，继续下一版。

用户拒绝执行方案时，不开始变更。备份失败时，不执行脚本。脚本失败时，不进入文档修改阶段。必需项未完成时，不记录目标版本。

文档合并保留用户已有决定。新说明与用户约束冲突时，模型说明差异并请求决定，不能静默替换更严格规则。

最后一版完成后，提示使用 Pi 原生 `/reload`。不自动重载，也不自动继续研究或交易任务。

## 6. 中断、接续与幂等

程序保存当前升级批次、已完成版本和各阶段进度。这是专用升级进度，不是通用任务运行时，不替代 Pi 原生会话恢复。

中断后不自动继续。用户再次执行 `/ffa update` 时，程序依据进度和实际状态接续。

已完成且验证有效的程序阶段不重复执行。脚本仍须保证重复执行安全，以应对变更已保存但阶段记录尚未保存的中断。不能仅凭聊天记录判断脚本是否完成。

模型接续文档阶段时重新读取当前资料。已符合要求的内容不重复追加，只处理缺项或冲突，不直接重放旧编辑。

所有要求完成后才更新该版工作区版本。版本记录失败时，不宣称完成；再次执行时核对已有结果，不盲目重做。

## 7. 备份与历史保留

每版执行前，在 `.ffa/` 内按源版本和升级批次保存备份。备份包括：

- 本次升级会修改的内部文件和工作区文档。
- 一致的内部数据库快照。
- 恢复所需的文件清单，包括升级前不存在、计划新建的文件。

数据库使用可靠的快照方式，不直接复制正在写入的数据库文件。备份范围不能递归包含历史备份目录。

历史备份永久保留，不自动清理。接续同一批次时保留原始升级前备份，不能用中断后的状态覆盖它。

不提供回滚能力，也不承诺备份可以安全覆盖当前工作区。失败时报告已完成、未完成和需要处理的事项，优先接续升级。不能通过旧快照恢复丢失后续交易记录。

## 8. 完成检查与模型边界

模型通过 `ffa_update_workspace` 提交文件方案及接续请求，通过 `ffa_finish_update` 提交完成结果。不能直接修改工作区版本或升级进度。`.ffa/` 内的全部变更由程序执行。

完成工具核对：

- 当前实例、源版本和升级批次仍有效。
- 程序阶段完成且验证通过。
- 该版可检查的文档条件已满足。
- 必需项没有未解决事项。
- 用户确认该版升级完成。

程序检查只证明可检查的条件成立，不证明文档内容、模型判断或外部事实完全正确。用户确认不授予交易许可。

内部变更摘要需要明确业务影响，但不要求模型了解内部存储细节。模型不能通过文件工具直接修改 `.ffa/`。现有工具拦截也不构成对 Bash、Python 或其他扩展的强隔离。

## 9. 模块责任

实现时沿用现有架构边界，不建立升级插件平台。

| 模块 | 责任 |
| --- | --- |
| `src/extension/` | 命令入口、启动提示、Pi 会话交互和重载提示 |
| `src/services/` | 升级链、阶段顺序、接续、完成规则及脚本协调 |
| `src/storage/` | 工作区版本、阶段进度、可靠写入和一致备份 |
| `src/tools/` | 模型可见的升级结果契约与完成工具 |
| 包内升级资源 | 每版独立脚本、声明和说明 |

服务只接收普通数据及必要的窄能力，不接收完整 Pi 上下文。命令和专用工具使用同一升级服务。脚本调用所属内部状态服务或存储入口，不绕过所有权及可靠写入规则。

## 10. 验证要求

本地测试使用真实文件、SQLite 和 Pi SDK，重点验证：

- 基础版本识别、无标识不处理和初始化状态限制。
- 完整升级链、缺失节点、版本过高和无需升级时无副作用。
- 逐版完成，失败不进入后续阶段或后续版本。
- 备份完整、一致、不递归，历史备份不被覆盖。
- 脚本幂等，以及变更保存与阶段记录之间的中断。
- 文档必需条件未满足或用户未确认时，版本保持不变。
- 完成记录失败后的安全接续。
- 历史交易和结果不明记录在升级后仍保留。

不使用假模型、模拟能力提供方、真实交易或个人凭据。不用提示词文本断言证明模型行为，不增加文件哈希校验。

真实模型的方案整理、文档合并、冲突处理和跨会话接续，需要获准环境验收。本地测试不能证明这些行为已经正确。

## 11. 当前实现与逐版资源

- `src/services/workspace-update-service.ts` 管理链检查、阶段顺序、接续和完成。
- `src/services/workspace-update-contract.ts` 定义每版声明和程序方法。
- `src/services/upgrades/index.ts` 显式注册包内版本脚本，目标版本当前为 1。
- `src/storage/workspace-update.ts` 检查进度与文件范围，发布不可覆盖的备份。
- `src/tools/workspace-update.ts` 定义方案工具及完成工具。
- `resources/prompts/workspace-update-request.md` 提供共同的模型操作边界。

后续每版在 `src/services/upgrades/` 提供独立脚本，并将独立模型说明放入包内 `resources/`。在注册表中明确列出脚本，不动态加载用户目录中的脚本。

声明包括 `from`、`to`、业务摘要 `summary`、说明文件 `instructions`、内部文件 `internalFiles` 和必需资料 `documents`。数据库自动纳入备份，不把数据库文件、所有权文件或历史备份目录列入普通文件范围。资料方案使用工作区内的具体文件路径，拒绝符号链接、目录和越界路径。

`preflight` 不修改状态，且须支持接续时的已完成效果。`apply` 只执行明确要求的内部变更，重复执行安全。`verify` 识别已保存的效果。`validateDocuments` 检查该版能检查的资料条件。没有内部变更时仍提供空操作及明确的验证条件。

所有声明摘要必须说明权限等业务影响。模型可见结果只返回业务摘要、模型说明、资料清单及阶段，不返回内部文件清单或备份路径。

本地验证覆盖真实文件、SQLite 快照、阶段与版本写入故障、逐版完成及 Pi 源码加载。测试用的本地版本要求不属于生产升级链。没有引入新的存储格式或通用格式转换能力。
